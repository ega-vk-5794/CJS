CJS Fault Finder

Where to put the breakpoint, in the order that finds it fastest. Written from the faults that actually cost us days — the payment that never read, the field that ate what you typed, the case id that was the string CJS.

Start with what is different, not with where it hurts.

D001’s payment page never opened. Three rounds went into the gateway, the department map, DFKKOP and the payment screen. The actual cause: ZCL_D001_SCHOOL_LIC_INIT_LOGIC redefined PREPARE_PAYMENT with nothing in it, so payment preparation never ran on that one journey. Every other journey paid fine because none of them redefine it.

If one journey misbehaves and the rest are fine, the framework is not the suspect. Open that journey’s handler class first, every time.

02 · Fast lookup

Symptom → first breakpoint

One line each. Set the breakpoint, launch with &trace=x, and you will know within one round trip whether you are in the right method.

SymptomBreak here first
One journey differs, the rest work the journey’s own handler class — the method matching the symptom An empty redefinition is a deletion, not a no-op. Look for a body that is only a commented-out CALL METHOD SUPER->. Four hooks do real work in the base: ON_CUSTOM_VALIDATE (the PAID gate), RENDER_FIELD (the fee card), ON_POPUP_EVENT, PREPARE_PAYMENT.
Field draws, accepts typing, is empty next round trip ZCL_RAK_JOURNEY_RENDER->BIND_OF Returns blank when ASSIGN COMPONENT misses — the control binds to nothing, silently. Also check the ftype: NUMBER/CURRENCY once passed type='Number', and an HTML number input blanks any value that is not a clean numeral.
Pay pressed, no tab, no message ZCL_RAK_JOURNEY_LOGIC->PREPARE_PAYMENT, first line Three exits before the CPG read — NOCASE, NOSCREEN, and the DFKKOP open-item miss — and each traces its own name. Total silence means the method never ran, so suspect the handler’s redefinition.
Gateway opens, payment never confirms ZCL_RAK_PAY_ENGINE->POLL_STATUS DEV_AUTOPAY( ) short-circuits to SUCCESS on E10 only, so the real path first runs in QA. Check the RFC destination ZREAD_PAY_STATUS_DEST and whether ZETISLAT_TRANSAC is being written.
Journey opens empty / read returns nothing ZCL_RAK_QNV_BRIDGE->READ, after the CALL FUNCTION Check ET_VALUES count. Zero values with zero messages means the BAdI found neither case nor draft — usually the launch key is the wrong shape: SCMG_T_CASE_ATTR-EXT_KEY and a VIBDCHARACT INTRENO are different values.
Grid empty, or a column shows its neighbour’s value ZCL_RAK_JOURNEY_BE->BACKEND_READ_GRIDS Cells are positional at both ends. CJS reads FIELD1..n into spec columns 1..n; the BAdI writes 'FIELD' && LIST_SEQUENCE. Two columns sharing a sequence, or a blank one, and nothing reports it.
Field or whole section vanishes ZCL_RAK_JOURNEY_BE->APPLY_CTRL SET_HIDDEN( ) writes the handler-override table, which outranks ZRAK_T_JNY_RULE and the configured flag. Under &trace=x the CTRL the BAdI HID: line names the fields.
A press does nothing at all ZCL_RAK_JOURNEY_ENGINE->Z2UI5_IF_APP~MAIN, the event CASE An event name the dispatcher does not match is silent. Match with CP, never an offset: IV_EVENT is a STRING and iv_event(8) on a six-character name raises CX_SY_RANGE_OUT_OF_BOUNDS.
Server-side change does not appear on screen ZCL_RAK_JOURNEY_RENDER->SEND_VIEW Hashes the markup and sends a model-only update when it matches. Correct by design — but if you changed something that does not alter the markup, this is why the page looks stale.
Config edited, journey unchanged ZCL_RAK_CJ_CFG_CACHE=>GET Config is cached per journey. A teardown or an edit outside the Studio needs INVALIDATE( ).
Uploaded documents gone after Back ZCL_RAK_JOURNEY_RENDER->RENDER_CHIPS Draws staged files from MT_ATTACH and the case’s own from MT_BE_ATTACH. Empty uploader with files on the case means the second list is not arriving — check IDENTIFIER1, which carries the field name.
Case id blank inside the BAdI ZCL_EGA_CJ_*_ABS->ZIF_EGA_FW_CJI~MAPPER GS_DATA is restored by RETRIVE_DATA( ) from INDX(CJ), not built from what CJS sends. READ then passes the key as IV_DRAFT, never IV_CASE_ID.
Injected JavaScript does nothing, on a round trip that opens or redraws a POPUP whether the snippet RAN — not what it does FOLLOW_UP_ACTION( ) fires from the main view’s onAfterRendering, and a round trip that only reopens a dialog need not re-render the main view. Cost four rounds on the popup attachment scroll and six on the parcel map, both spent editing a snippet that was never executed. Three failed variations of the same snippet is the tell — the fourth will fail too. Carry it in an inline event attribute as well: a 1×1 data-URI <img onload> renders inside the dialog fragment and fires when its DOM is inserted, the same channel RENDER_UPLOADER( )’s onchange has always used. Make the payload idempotent so both channels may run.
A registered paragraph, override or catalogue entry renders as the plain ZLABEL — the field looks unconfigured what MS_CONFIG-JOURNEY_ID actually holds A ZRAK_T_JNY key is the full spelling — DOK_D002_SCHOOL_LIC_NEW — while every entry in ZCL_RAK_TEXT, and everyone discussing these journeys, says D002. LONG( ) and GET( )’s override read both matched it with an exact READ TABLE, so the whole DOK family missed — and LONG( ) returns IV_DEFAULT on a miss, so there is no error, no trace, and a declaration that renders as the single word “Declaration”. JNY_MATCH( ) is the one test now: exact first, then the id split on _ with the key having to equal a whole segment (a segment, not CS/CP, or D001 would also answer for a DOK_D0012_*). The general form: a lookup keyed on a name a human typed, against an id a table generated, misses silently whenever the two spellings are a convention rather than one value.
A field shows a real, correctly-spelled sentence — just the wrong one. Nothing is blank, nothing errors whether the CATCH you are relying on can fire at all D001’s payment note rendered as the word “Next”. DEFAULT_VAL was TEXT:@D001NOTE, and three call sites wrote CONV symsgno( lv_no ) inside a TRY, each documenting the CATCH as the branch a non-numeric reference takes. None ever reached it. A character source assigned to a type N target has its non-digits discarded and the digits right-aligned — silently, no exception — so 'D001NOTE' becomes 001, which is C_NO-NEXT, and the catalogue correctly served it. ZCL_RAK_TEXT=>MSGNO_OF( ) is the guard now. The general form: a comment asserting which branch runs is not evidence that it runs. A conversion that is documented as failing, a CATCH nobody has watched enter, a fallback whose output happens to equal the success path — all of them look identical to working code. Prove the branch executes before you edit what is inside it.
03 · Reading the trace

Lines worth knowing

Launch with &trace=x. E10 only — quality and production show nothing, whatever is appended to the URL.

KEYSHAP '…' SCMG_T_CASE_ATTR HIT / VIBDRO HITWhat shape the launch key is. A hit on the first means a real case; a hit on the second means a real-estate INTRENO was handed over where a case was meant.
BUFFER INDX(CJ) id '…' cleared (row existed)The DOK/EPDA draft store was dropped before the entry read. (no row) on a relaunch means nothing is re-seeding it.
READ … n value(s) back · n message(s)Zero values and zero messages is the quietest failure in the framework: page renders, every field blank, looks like a citizen who has typed nothing.
READ grid X NOT overwritten · the citizen's copy winsGrid protection working. Scalars have no equivalent — only blank backend answers are skipped.
CTRL the BAdI HID: A, B, CFields the legacy field control hid on this read. Outranks every CJS-side reason for them to be visible.
BIND <field> has NO model componentThe control will draw, accept typing and lose the value. Either the field is not in ZRAK_T_JNY_FLD, or its name exceeds 23 characters.
PAY dfkkop open item … found on ext_key …The open-item gate passed and the CPG read is about to run. Its absence, with no other PAY line, means PREPARE_PAYMENT never executed.
GATE n BLOCKER(S)Configuration defects ZCL_RAK_CJS_XCHECK found. “Must not go to QA until cleared” is meant literally.
SLOW … took n msTime spent waiting on the backend, not rendering. Read the per-call lines above it.
04 · Method

Rules that shorten the hunt

Verify by content, never by status

costs days A pull writes the source and leaves the object inactive; the runtime keeps running the old version while the Class Builder shows the new one. Implemented / Active proves nothing. Open the method and look for a string you added.

Silence is evidence

Every path through a well-instrumented method traces something. If a method has four possible exits and all four are silent, it did not run — which is a completely different problem from any of the four.

Two rounds with no visible change → instrument, stop theorising

A message_strip that renders unconditionally settles in one round trip what inference will not settle in five. Every diagnostic in the table above exists because guessing came first.

Compare the working case against the broken one

Same journey on two systems, or two journeys on one. The variable between them is the bug — a handler version, a client, a config row. This is faster than reading either one in isolation.

Positional means silent

Grid cells, backend table columns, hand-built rows: all positional at both ends, with the two orders set in different places. A mismatch renders the neighbouring value and raises nothing. Line the spec up against /QNV/SB_UI_DEFIN before believing it is a rendering bug.

Environment before code

E10 / E20 / E30 Dev stubs (DEV_STUBS_OK), auto-pay (DEV_AUTOPAY) and the trace itself are all E10 only. Anything that works in dev and not in QA is that gate before it is anything else.

05 · Worked example

How the D001 payment fault should have gone

Symptom — Pay pressed, waiting card, gateway never opens. Every other journey pays.

Rule 4 — compare. One journey differs ⇒ the handler, not the framework. 30 seconds

Rule 2 — silence. PREPARE_PAYMENT has four possible trace lines and produced none. It did not run.

Breakpoint. ZCL_D001_SCHOOL_LIC_INIT_LOGIC->PREPARE_PAYMENT — body is a commented-out SUPER-> template. Found.

What it took instead: the gateway route, ZDT_PG_DEP_MAP, the DFKKOP key width, the payment screen configuration, and three wrong diagnoses — all of them upstream of a method that was never called.

Written against main after the D001 payment, attachment and NUMBER-field hunts. Breakpoints are method names, not line numbers — lines move, methods do not. Add a row whenever a fault costs more than one round trip to find.
